# MRIO API and EXIOBASE source-boundary refactor plan (2026-06-17)

## Scope and decision summary

This plan keeps the immediate patch sequence specific-first and generic-second. The immediate correctness boundary is that a requested EXIOBASE DOI/version must map to the exact source zip being read. Only after that boundary is reliable should the MRIO API be generalized.

The current policy decisions are:

- Keep `load_mrio(dataset="exiobase")` disabled for full EXIOBASE `pymrio.IOSystem` loading until an explicit large-load opt-in is designed.
- Keep `load_mrio_matrices()` backward-compatible: it continues to return `A, x, y, basis_index, metadata` by default.
- Use `download_log.json` as the source-zip provenance file for EXIOBASE DOI/version verification.
- Convert EXIOBASE region slices to direct zip streaming in Phase 2, with persistent slice caching disabled by default.
- Move to a generic MRIO source/request/result API only after the EXIOBASE source and slice behavior is correct and tested.

## Phase 1: EXIOBASE source zip DOI/version verification

Patch target: `src/ecolecon_mrio/data.py`.

Behavior:

1. Normalize requested DOI values so both `10.5281/zenodo.20051562` and `https://doi.org/10.5281/zenodo.20051562` compare equal.
2. When `IOT_<year>_<system>.zip` already exists, read `download_log.json` or compatible local download-log JSON candidates.
3. Extract the recorded DOI/version token.
4. If no DOI/version is recorded, fail loudly unless `force_download=True` has already removed/replaced the zip.
5. If the recorded DOI/version differs from the requested DOI/version, fail loudly and instruct the user to use `force_download=True` / `--exio-force-download`.
6. After new downloads, ensure `download_log.json` contains the normalized DOI/version used for the download.

Tests:

- Existing zip plus matching `download_log.json` is accepted.
- Existing zip plus mismatched `download_log.json` is rejected.
- Existing zip plus missing DOI/version provenance is rejected.
- Existing DOI URL normalization and split-script DOI pass-through tests continue to pass.

Out of scope:

- Region-slice direct streaming.
- Generic MRIO provider refactor.
- Re-enabling full EXIOBASE `load_mrio`.

## Phase 2: Direct EXIOBASE region slices from the source zip

Patch target: `src/ecolecon_mrio/exiobase3.py` and split-pipeline call sites.

Behavior:

1. `load_exiobase3_region_slice()` calls the DOI-checked source boundary, not `load_mrio(dataset="exiobase")`.
2. Default `cache_region_slice=False`.
3. Default behavior streams `x.txt`, `Z.txt`, and `Y.txt` from the source zip and returns an in-memory `ExioRegionSlice`.
4. Domestic/import/total flows are computed from streamed rows/columns without materializing the full `pymrio.IOSystem`.
5. Optional `cache_region_slice=True` may write/read `Z_*.pkl`, `Y_*.pkl`, and `x_region.pkl`, but only with metadata checks for DOI, year, system, region, and flow.
6. `load_exiobase3_region_slices()` should read multiple flows/regions efficiently where practical, but correctness comes before one-pass optimization.
7. Remove no-op `doi=args.exio_doi,` statements from split scripts.

Tests:

- Clean-cache region slice does not call `load_mrio(dataset="exiobase")`.
- `cache_region_slice=False` writes no slice pickle files.
- Returned slices match expected index labels and flow semantics on a tiny synthetic EXIOBASE-like zip.
- Split scripts still forward `--exio-doi` to every region-slice call.

## Phase 3: Matrix-result API without breaking compatibility

Patch target: `src/ecolecon_mrio/data.py` or a new focused module if it reduces coupling.

Behavior:

1. Introduce a result object such as `MrioMatrixResult` or `ExiobaseMatrixResult`.
2. Allow callers to request `A`, `Z`, or both, and final demand as `summed`, `matrix`, or `none`.
3. Keep `load_mrio_matrices()` as a backward-compatible wrapper returning `A, x, y, basis_index, metadata`.
4. Share low-level zip readers with the region-slice implementation where appropriate.

Out of scope:

- Full provider abstraction for every dataset.

## Phase 4: Generic MRIO source/request/result API

Patch target: public API module and docs.

Behavior:

1. Introduce generic source descriptors, for example `MrioSource(dataset, year, version, system, data_root)`.
2. Introduce request/result objects for full MRIOs, global matrices, and region slices.
3. Move dataset-specific mechanics into providers.
4. Treat EXIOBASE DOI as `source.version` at the generic API boundary; only the EXIOBASE provider interprets it as a DOI.

Compatibility:

- Keep existing public wrappers during a transition period.
- Deprecate EXIOBASE-specific arguments on generic `load_mrio()` only after replacement APIs are available.

## Phase 5: `load_mrio()` cleanup

Behavior:

1. Keep `load_mrio()` as a generic full-object loader.
2. Do not silently perform large EXIOBASE full-object loads.
3. If full EXIOBASE load is restored, require an explicit opt-in such as `allow_large_load=True`.
4. Remove or deprecate EXIOBASE-specific cache knobs from the generic signature once provider-specific configuration exists.

## Phase 2 implementation note

Phase 2 changes `load_exiobase3_region_slice` to stream region use slices directly from the DOI-checked EXIOBASE source zip by default. Persistent derived slice pickle caches are optional (`cache_region_slice=True`) and are off by default to avoid zip/slice provenance divergence. Optional slice-cache metadata must include year, system, region, flow, and normalized EXIOBASE DOI; stale metadata must fail unless rebuilt.


## Phase 3 implementation note

Phase 3 introduces `MrioMatrixResult` and `load_mrio_matrix_result(...)` as the structured matrix-result boundary for EXIOBASE zip-stream reads. The result API can return `A`, `Z`, or both, and final demand as a summed vector, full matrix, or not at all. `load_mrio_matrices(...)` remains the backward-compatible tuple wrapper around `matrix="A"` and `final_demand="summed"`.
